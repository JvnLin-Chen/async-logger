# 工业级多线程异步日志库

## 当前版本：v3 - 有界队列与溢出策略
- **v1**: 最小异步闭环（队列 + 单后台线程 + 基础停机），10000条测试通过。
- **v2**: 重构 `FileWriter`，文件句柄保持常开，支持跨天无缝切换，增加空指针及异常防御。
- **v3**: 引入有界队列，实现 Overrun Oldest 丢弃策略，增加无锁监控计数器。

## v3 验收结果
| 测试项 | 结果 |
|---|---|
| 压测环境 | 模拟慢磁盘（后台每写一条 `sleep 1ms`），主线程狂写 50000 条 |
| 溢出测试 | 实际写入 10169 条，丢弃 39831 条，无内存泄漏 |
| 逻辑校验 | 写入 (10169) + 丢弃 (39831) == 总数 (50000) |
| 并发安全 | 多线程下 `drop_count` 计数精准，未发生数据竞争 |

## v3 关键设计决策
1. **有界队列**：限制队列最大容量为 10000 条，防止极端情况下内存被撑爆。
2. **丢弃策略（Overrun Oldest）**：当队列达到上限时，踢掉队头最旧的日志，存入最新日志，确保业务线程绝不阻塞。
3. **无锁监控**：使用 `std::atomic<int> drop_count`，业务线程自增、外部线程读取均不需要加锁，保证监控行为不影响主流程性能。
4. **局部变量隔离**：`dataPush` 内部使用局部变量 `is_drop` 记录本次是否发生丢弃，出锁后再通过 `atomic` 自增，缩短锁的持有时间。

## v3 踩坑与疑惑记录
- **坑1（数据踩踏）**：误将 `is_drop` 写成类成员变量，导致多线程并发修改时状态被覆盖，计数错误。修复：改为函数内局部变量，每个线程独立维护。
- **坑2（编译报错）**：`dataPush` 参数传入非 const 引用导致无法接收临时字符串。修复：传值 + `std::move` 入队。
- **坑3（边界少判）**：写成了 `size() > max_size`，导致容量超标。修复：改为 `size() >= max_size`。
- **疑惑1（atomic 原理）**：为什么 `std::atomic` 可以不加锁自增？- 
**解答**：普通的 `int count++` 在 CPU 层面是三步（读内存、寄存器加 1、写回内存），多线程同时执行会互相覆盖（丢失更新），必须加锁。
- **`std::atomic` 的本质**：它底层使用了 CPU 的硬件级原子指令（如 x86 的 `lock add`）。这条指令在执行期间，别的 CPU 核心无法插足。因此它的自增是一个不可分割的整体，不需要操作系统介入挂锁，性能极高。
- **为什么放在锁外**：把 `drop_count` 设为 `atomic` 后，业务线程自增、监控线程读取（`.load()`）都不需要去抢 `mutex` 锁，避免了监控行为阻塞业务线程。

- **疑惑2（锁粒度）**：为什么不在锁内直接 `drop_count++`？
 **解答**：这涉及“锁的粒度”。如果我们在锁内直接 `drop_count++`，虽然安全，但会拉长持锁时间。通过局部变量记录是否丢弃，等出了 `mutex` 作用域，再安全地利用 `atomic` 自增，这是为了极致的性能妥协。

## 个人核心收获
1. **局部变量是并发的天然隔离区**：多线程执行同一个函数时，成员变量是公共的（需要保护），但函数内部的局部变量是每个线程私有的（绝对安全）。能用局部变量解决问题的，绝不上升到成员变量。
2. **“测不准”往往是因为“环境没造好”**：验证溢出策略时，如果只死循环写，后台可能早就写完了，根本测不出。必须人为让后台线程 `sleep`，强行制造“消费慢于生产”的极端工况，才能逼出真实的表现。
3. **防御性编程的底线**：涉及到除法、取模、容器操作（如 `front()`）之前，必须先做空指针或空容器判断。因为多线程环境下的状态转瞬即逝。
